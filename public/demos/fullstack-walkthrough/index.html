Engineering walkthrough / about five minutes

From the interface to the state behind it.

I build interfaces, APIs, and the data flows connecting them. Here are five decisions I can explain and the evidence behind them. This is a guided case-study tour, not a recording of a production incident.

01 / Start with the user

A failed request can leave more than an error.

Content Generator reserves credits and calls an AI provider. A stopped request can leave accounting and content at different stages. The next execution needs to know which work already happened.

Open the case study and architecture

02 / Make progress durable

One attempt owns the job.

A durable claim identifies the current owner. An attempt token stops an old worker from saving a late result after ownership changes. A checkpoint lets recovery reuse a saved provider response.

The selected local tests cover overlapping claims, expired ownership, and lost acknowledgements. They reconstruct interrupted states; they do not terminate a production Worker.

Read the 70-test result

03 / Respect uncertainty

A timeout does not prove the provider did nothing.

I distinguish a rejected request from an unknown outcome. Bounded retries are appropriate for explicit rate-limit rejection. Blindly repeating an uncertain paid request can repeat work and cost.

Read the limits and reproduction command

04 / Connect it back to the screen

The balance was saved, but the sidebar was stale.

The earlier local browser run exposed a cache consumer that was not subscribed to session changes. Connecting the consumer to updates made the UI reflect the saved balance. The screenshot records the display; database and API assertions establish accounting correctness.

Open the case study for the frontend state explanation

05 / Check usefulness separately

Valid data is still a draft for a teacher to review.

Teacher Exam connects generation, saved history, review, and A4 printing. Technical checks establish specific behavior. Real teacher sessions are needed to establish where the workflow helps and where it gets in the way.

I have prepared a pilot for 3–5 teachers. I am not presenting its results before those sessions happen.
